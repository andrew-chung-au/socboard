# Delivery pace (human ruling, 2026-11-12)

Applies to the orchestrator in this repository. The human ruled these after #9, #10 and #74 took two to four human hand-overs each.

1. **CI is the test loop.** Push the issue branch and open a draft pull request early; CI runs `make install` and `make verify` on every push, and on a pull request its weakened-test check compares with `main`. Read results with `gh api repos/<owner>/<repo>/actions/runs?branch=<branch>`, then `.../actions/runs/<id>/jobs` and `.../actions/jobs/<id>/logs`. QA cites the run id and the log lines as evidence ("CI-VERIFIED"). Ask the human to run only what CI cannot: `uv add` (the lockfile), starting servers, a browser, Docker.
2. **One pull request per issue.** Commit the session summary, and any roadmap or supporting-list update, on the issue branch before the human merges. A separate pull request only for work outside any issue.
3. **Groom ahead in batches.** While the current issue waits, the PM may check or groom the next two or three Core issues; the human approves them in one sitting. This overrides "groom only the next issue" for this repository.
4. **One extra issue in flight**, limited to small supporting issues (for example #60, #62), while the main issue waits on the human or an outside reviewer. Never two Engineer launches on Core issues at once.
5. **Light tier for docs-only changes** is queued for the epoch batch (`LIGHT_ALLOWED` in `agent-kit.conf`, protected); until it lands, docs changes follow the normal path.
6. **The Heavy second QA launch is a new session** (interim rule until sweep 4 decides the kit change, `_docs/planning/sweep-4-candidates.md`, item 1). Its launch message tells the reviewer: "If this session has already reviewed, implemented or discussed this issue, stop before reviewing and say so." When the result comes back, check its comment states a new session; a launch that does not is discarded and run again (`process.md`, Tiers). A fresh subagent with no shared context also counts (the human allowed it on #13, #99 and #14). The launch message tells a blind second launch to exclude `.scratch/qa-*`, `.scratch/engineer-*` and `.scratch/issue-*.json` from every search, or to limit searches to `socboard/**` and `tests/**`, and to read the issue body only through a body-only extract (sweep 5, item 5; on #14 a broad search leaked earlier QA lines).
7. **A Medium-or-higher QA finding has to be fixed (human ruling, 2026-11-13).** QA's stopping rule: a Medium-or-higher finding fails the verdict and goes back to the Engineer; Low findings go in the report and do not fail it. QA does not pass over a Medium because a decision record already names it as an accepted trade-off. The only way a Medium ships unfixed is the human's explicit ruling at the decision point, recorded in the session summary. A launch message never calls a stopping rule "agreed with the human" unless the human said so in this session. Reason: on #63 the third QA run and the Heavy second launch were told to pass over gaps the record had accepted, and one Medium was reported as "accepted by the decision record" under a rule the human had not agreed to; the human later accepted the trade-off at the decision point, but that call is the human's, not QA's. This rule governs the Heavy second QA launch too (human ruling, 2026-11-13, on #139, recorded in the Orchestrator comment https://github.com/andrew-chung-au/socboard/issues/139#issuecomment-6869773094): `_docs/agent-kit/team/qa-engineer.md` says any problem in that launch is a FAIL, but in this repository a Medium-or-higher finding fails it and Low findings go in the report; the launch message says so.
8. **No closing keyword before an issue number in a PR title or body either (human ruling, 2026-11-13).** A pull request title or body never contains close, closes, closed, fix, fixes, fixed, resolve, resolves or resolved followed by `#N`, not even in a warning. GitHub closes the issue at merge and skips the Close gate, and the issue gets no Close comment. Write "the orchestrator closes issue 19 after the merge" instead. This is the rule `software-engineer.md` states for commit subjects, extended to PR text. Before opening a PR, scan it: `gh api repos/<owner>/<repo>/pulls/<n> --jq '.title + " " + .body'` and look for a keyword next to a number. Reason: #99 (a commit subject) and #19 (the PR body said "the orchestrator closes #19") were both closed by GitHub at merge with no Close comment.
9. **After two QA FAILs in a row on one criterion, ask the human before the third run (sweep 6, proposal 3).** Ask which gaps are accepted (a Medium or higher only by the human's ruling, item 7), which kinds of finding still fail, and what the decision record will say. The third launch is given that list. Reason: #63 had four QA runs and three protected-file diff approvals before a stopping rule was written down.
10. **A Reviewer launch says "write nothing, not even under `.scratch/`" (sweep 6, proposal 4).** In Kiro Web the Reviewer is a general task held read-only only by its launch message, and `make assert-clean` cannot see git-ignored paths such as `.scratch/`. List the `.scratch/` file names before and after each Reviewer launch and report any change.
11. **In Kiro Web the search tool does not index `_docs/` (sweep 6, proposal 6).** Search it with `grep -rn` through the shell, and a claim-time or grooming check of `_docs/` names the command it used, so "no match" means something.
12. **Name no env file in a comment (sweep 6, proposal 5).** Put this sentence in every QA and Engineer launch message: "Name no env file in a comment; write 'an env file' instead, because the comment scanner refuses the name." The scanner refused QA text on #80 and #21.
13. **Limit review rounds (human ruling, 2026-11-14, after #139 took eight Engineer rounds).**
    - **One Reviewer pass per issue**, after the first QA PASS. Its findings go to the human once. Only findings the human marks "must fix" are applied before the merge; the rest become follow-up issues or are dropped. The Reviewer does not run again after a fix round.
    - **A fix round gets one QA re-check of the changed lines only**, by one fresh QA launch, even on a Heavy issue. The independent second launch runs once, on the first complete version.
    - **Decision records and docs-only issues are proposed as Standard**, not Heavy, unless they change a security boundary in code or CI.
    - **After two fix rounds on one issue, stop and ask the human "ship or fix?"** with the open findings listed, before a third round.
    - **The orchestrator never applies a finding on its own recommendation** if it changes approved issue text or an approved decision; that goes to the human.
    - **Records do not track live status** (which items are filed, which pull requests merged); the roadmap and the tracker do.
