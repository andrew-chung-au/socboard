Title: Build one container image of the app and the built frontend, and build and check it in CI

## Why

The spec's Deploy stories need one container image that serves the web app and the API from one origin. Nothing builds one: there is no `Dockerfile`, and CI only runs `make verify`. The sandbox has no Docker, so CI is where the image gets built until the human tries it once. What goes in the image, how it starts and what it trusts are security decisions, so the checks that can run without Docker (a static test of the `Dockerfile`, a checker script with unit tests) go into `make verify`, and the checks that need Docker run in one new CI job.

## Goal

A `Dockerfile` builds the image from the repository, CI builds it on every push and pull request and checks what is in it, and the image runs the app as a non-root user, on one worker, with nothing secret or demo-related in it.

## Acceptance criteria
- [ ] A multi-stage `Dockerfile`. Stage 1 builds the frontend: `bun install --frozen-lockfile`, then `bun run build` with `VITE_USE_MOCK=false` set as an `ENV` (not an `ARG`, so an image cannot be built with the mock on); `VITE_FEATURE_REASSIGN` and `VITE_POLL_INTERVAL_MS` are build arguments; `VITE_API_BASE_URL` is not set anywhere, so the client uses `/api`. Stage 2 is based on Python 3.12 (the version #100 pins), installs the locked runtime dependencies only (no dev group), copies `socboard/` (with its migrations), `pyproject.toml`, `uv.lock`, `.python-version`, `README.md` (the project metadata names it) and the built `dist`, and runs as a numeric non-root user. Layout: the app under `/app` (`/app/socboard`, `/app/frontend/dist`, the virtual environment at `/app/.venv` first on `PATH`), which is where the app's default static folder (`frontend/dist` beside `socboard/`) already points.
- [ ] The start command is `python -m socboard.server --allow-non-loopback-host` in exec form, with `SOCBOARD_HOST=0.0.0.0` set in the image (#142: the flag, not the variable, is what lets the server bind it). **One worker:** the command has no `--workers` and the image sets no `WEB_CONCURRENCY`, because the in-process limits of #178 and #183 assume one worker (decision 9 of `_docs/decisions/2026-11-13T2156Z-deploy.md`). **Forwarded addresses:** the image does not set `FORWARDED_ALLOW_IPS`, so uvicorn keeps its default (`127.0.0.1`) and never believes a forwarded header from another address. The image cannot know the proxy's address, so it does not set `SOCBOARD_TRUSTED_PROXIES` either; whoever runs the container (D11 for Compose, D17c for the server) sets `SOCBOARD_TRUSTED_PROXIES` to the proxy's address (README, "Login attempt limits"), and if they set `FORWARDED_ALLOW_IPS` at run time it lists only that proxy. Never `*`: it would let any caller's `X-Forwarded-For` choose its bucket in the login limiter. The image also contains `python -m socboard.migrate` and `python -m socboard.seed` as one-shot commands (D11 and D20 run them).
- [ ] A static test, `tests/test_dockerfile.py`, runs in `make verify` with no Docker and fails when the `Dockerfile` does any of these: starts without `--allow-non-loopback-host`, uses `--workers` or sets `WEB_CONCURRENCY`, sets `FORWARDED_ALLOW_IPS` at all (in an `ENV` or `ARG` line, and in particular to `*`), sets `SOCBOARD_TRUSTED_PROXIES`, runs the last stage as root (no `USER`, or `USER root`/`0`), sets `VITE_API_BASE_URL`, passes `VITE_USE_MOCK` as an `ARG`, names any secret setting from `socboard/settings.py` (every entry with `secret=True`) in an `ENV` or `ARG` line, or has a final `FROM` whose Python major.minor differs from `.python-version`. One test case per refusal, using small Dockerfile texts, plus one that the real `Dockerfile` passes.
- [ ] A `.dockerignore` keeps `.git`, `.scratch`, `node_modules`, every env file by name and by extension pattern except the example one, `*.db` and its journal files, `tests`, `_docs`, `_session-summaries`, `_human-tasks`, `terraform`, `.github`, `frontend/dist` and `frontend/node_modules` out of the build context. A static test checks each entry is present. The `Dockerfile` copies named paths only, never `COPY . .`.
- [ ] `scripts/check_image_files.py <folder>` (standard library only) checks a folder holding the image's files and exits 1, naming each finding and never printing a matched value, when it finds: a file or folder named like an env file (other than `.env.example`), `.git`, a database file (`*.db`, `*.sqlite*`, journal files), `tests`, a `test_*.py` file or `node_modules` under `app/` outside `.venv`; or, in the app-owned files (`app/socboard`, `app/frontend/dist`, `app/README.md`; the virtual environment is not scanned, it holds other people's code), a demo credential or hostile fixture (the patterns `make frontend-build` greps for: `analyst-a-pass`, `analyst-b-pass`, `lead-pass`, `<script>alert(`), a Google fonts host, or any line matching a pattern in `_docs/agent-kit/scripts/secret-patterns.txt`. Unit tests (`tests/test_check_image_files.py`) cover one refused case for each kind on a temporary folder, a clean folder that passes, and that every pattern in the secret list compiles in Python's `re`. The refused cases are shown by these tests, so no throwaway branch is needed.
- [ ] CI: a new workflow `.github/workflows/image.yml` (protected; the exact diff goes to the human) runs on every push and pull request, uses no secret, and has these steps, each failing the job: build the image (`docker build`); compare the image's Python major.minor with `.python-version` (a case that must be refused: a base image tag of another minor version fails it); export the image's files and run `scripts/check_image_files.py` on them; run the container with `SOCBOARD_MODE=deployed` and none of the settings and expect exit 2; run it with generated throwaway settings (a token secret, an ingest key and one seed password, made inside the step with `openssl rand` and masked in the log), then run `python -m socboard.migrate` and `python -m socboard.seed` in it, and expect `GET /api/health` to answer 200 and `GET /` to answer the entry page. No action other than `actions/checkout` is used.
- [ ] The image carries no cloud credential and no seeded password; the checks above are how that is shown.
- [ ] The README describes the image: the build command, the two build arguments, that `VITE_API_BASE_URL` stays unset, the start command, one worker, and the forwarded-address rule above in the same words as the login-limit paragraph (no new rule).
- [ ] The human builds the image once locally, runs it, and reports the result, the base image digests and whether `bun run build` needs Node as well as bun, in a task file under `_human-tasks/`, because the sandbox has no Docker. `VERIFY:` the base image tags and digests on the first CI build: `node` 24.22.0 and bun 1.4.2 for stage 1 (the versions `verify.yml` uses), `python:3.12` for stage 2, uv 0.13.6 (the CI version) copied in to install the locked dependencies; pin each by digest once known.
- [ ] `make verify` is unchanged except that it now also runs the two new test files, and it passes.

## Out of scope
- Pushing the image to a registry (D14).
- Compose, Postgres, the reverse proxy and a container health check (D11, D17c).
- Multi-architecture builds.
- Any change to `socboard/server.py`, the settings list or the limiters.

## Design

None. The static test and the checker script exist because the sandbox cannot run Docker: every rule that can be checked from the file text or from a folder of files is checked in `make verify`, and CI runs only what needs a Docker daemon.

## Constraints
- Files: `Dockerfile`, `.dockerignore`, `scripts/check_image_files.py`, `tests/test_dockerfile.py`, `tests/test_check_image_files.py`, `README.md` (its own section), `_human-tasks/` (the task file). Protected, as exact diffs for the human: the new `.github/workflows/image.yml`, and the `AGENTS.md` Layout line (add `Dockerfile` and `.dockerignore`). Nothing else is edited.
- Fixed values and where they come from: tool versions from `.github/workflows/verify.yml` (uv 0.13.6, Node 24.22.0, bun 1.4.2); Python 3.12 from `.python-version` (#100); the flag from #142; one worker and the in-process limits from decision 9 of the Deploy record; the forwarded-address rule from #178's README paragraph (uvicorn's `FORWARDED_ALLOW_IPS` default, `SOCBOARD_TRUSTED_PROXIES` for a proxy at another address).
- Depends on: #140 (the app serves the built frontend), #141, #142, #100, #178 and #183. All are merged to `main`.
- Proposed tier: standard (a new file set and a CI job, no new boundary; the start flag is #142's decision and the forwarded-address rule is #178's). Expected paths: as above.
