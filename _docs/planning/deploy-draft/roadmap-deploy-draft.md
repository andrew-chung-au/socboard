## Tasks, in order (proposed issues, one deliverable each)

1. **Record the deploy decision (Terraform on AWS).** Heavy decision record: Terraform on AWS mirroring vuln-triage, single server, region, state backend, how CI authenticates, what CI may apply, secrets, TLS hostname, accepted risks (readiness questions 2 to 6). Needs in Core: none. Who: Human decides; PM drafts.
2. **Serve the built frontend from FastAPI.** `/` and screen routes return the SPA (`index.html` fallback); unknown `/api/*` still gives the JSON 404 `not_found`. Needs: #10, #21, #27. Who: Eng; CI.
3. **Read configuration from the environment.** Database URL, ingest key, seeded-account passwords and poll interval come from env vars, with `.env.example`; in deployed mode a missing secret stops start-up (no weak fallback, unlike vuln-triage's dev default). Needs: #11, #13, #14. Who: Eng; CI.
4. **Run on Postgres.** Backend and migrations work on Postgres chosen by the database URL; SQLite stays the local default. Adds a driver dependency (approval first). Needs: #11. Who: Eng; CI with a Postgres service container.
5. **Prove single ownership on Postgres.** Two simultaneous claims leave exactly one owner, tested on Postgres (spec §5). Needs: #16, task 4. Who: Eng; CI.
6. **Allow a container to bind a non-loopback address safely.** The image listens on `0.0.0.0` through an explicit opt-in while `make backend-run` still refuses any non-loopback host. Needs: #10, #80. Who: Eng; human approves the protected-file change.
7. **Build one container image.** Multi-stage `Dockerfile` (build frontend, copy `frontend/dist` into a non-root Python image) that serves the full app on one origin. Needs: #21, #27, tasks 2, 3, 6. Who: Eng writes; CI builds and starts it; Human checks once on their machine.
8. **Add the Compose stack.** `docker-compose.yaml` with the app, a one-shot migrations step and Postgres (health check, data on a named volume), plus one `make` target. Needs: #22, tasks 4, 7. Who: Eng writes; CI or Human runs.
9. **Integration tests against the Compose stack.** Frontend served, backend reaches Postgres, login, ingest and queue work through the real stack. Needs: #14, #15, #22, task 8. Who: Eng; CI.
10. **End-to-end test of both journeys.** Browser test: claim, refused second claim, close with a reason, the Lead's audit-trail read, two analysts and a Lead. Adds a browser-test tool (dependency approval). Needs: #17, #19, #21, #22, task 8. Who: Eng; CI.
11. **CI builds the image and runs integration and E2E tests.** On every push and pull request: tests in parallel, build the image, then integration and E2E, beside `make verify`. Needs: tasks 9, 10. Who: Eng writes; CI is the check; Human pushes.
12. **Terraform: state bucket module (`terraform/bootstrap`).** S3 bucket (versioned, private, encrypted), applied once with local state and then migrated; README for the migration; `.gitignore` for state and real `*.tfvars`, tracked `*.tfvars.example`. Needs: task 1. Who: Eng writes; Human applies.
13. **Terraform: CI access module (`terraform/ci-access`).** GitHub OIDC provider (create or reuse), a read-only **plan** role, an **apply** role limited to the `infra` GitHub Environment and a **deploy** role limited to the `deploy` Environment; trust policies use the environment-form `sub` with the immutable owner and repository ids; the two-statement `ssm:SendCommand` policy; no stored keys. This module stays human-applied only (CI never changes its own roles). Needs: tasks 1, 12. Who: Eng writes; Human applies and sets the GitHub Environments and variables.
14. **Terraform: server module (`terraform/server`).** One EC2 instance (no key pair, SSM only), Elastic IP, security group (80 and 443 only), instance role (SSM plus read on named Secrets Manager secrets), encrypted data volume with snapshots, **Postgres data on that volume**, bootstrap that installs Docker, the Compose plugin and Caddy, a budget alert, `project=socboard` tag on everything. Needs: tasks 1, 12. Who: Eng writes; Human applies.
15. **CI: Terraform checks and plan.** On pull requests that touch `terraform/`: `fmt -check`, `init -backend=false`, `validate` (no credentials), then `plan` for the server module with the read-only plan role, posted as a PR comment or job summary. Pull requests from forks get no role. Needs: tasks 12, 13, 14. Who: Eng writes; CI; Human sets the plan-role variable.
16. **First apply by the human.** A human task and checklist: AWS account and budget alert first, GitHub Environments (`infra` with a required reviewer and no administrator bypass, `deploy`), apply bootstrap, ci-access, server in order, create the Secrets Manager secret, record the Elastic IP and hostname, then run `plan` again and expect no changes. Needs: tasks 12, 13, 14. Who: **Human**; Eng drafts the checklist.
17. **Deploy script and first deploy to the server.** A server-side deploy script run through SSM (pulls an image by tag, reads the secret with the instance role, writes the `.env` with restrictive permissions, runs Compose, reloads Caddy; a failed pull leaves the running version), plus the workflow step that calls it; the first deploy is run by the human and the public HTTPS URL loads. Image tag is `YYYYMMDD-HHMMSS-shortsha`, pushed to public GHCR with `GITHUB_TOKEN`. Needs: #22, tasks 1, 7, 8, 16. Who: **Human** (first run); Eng writes.
18. **Post-deploy smoke check.** A `make` target that, given a URL, checks `/api/health`, login, one ingest and that the alert reaches the queue within 5 s. Needs: #14, #15, #13. Who: Eng; CI and Human run it against the public URL.
19. **Deploy from CI on a green push to `main`.** The workflow deploys only after tests pass, using the OIDC deploy role, skips with a visible message if the server is stopped or `DEPLOY_ENABLED` is not `true`, records tag and digest in the job summary, then runs the smoke check. Terraform `apply` runs from CI only for the server module, on `main`, in the `infra` Environment after the human approves the plan. Needs: tasks 11, 15, 17, 18. Who: Eng writes; **Human** (repository variables, Environment approval); CI runs.
20. **Write the deploy and teardown runbook.** README and `_docs` say how to deploy, where the URL is, how to get credentials, the lessons from vuln-triage that apply, and how to delete every cloud resource in order (destroy server, then ci-access, delete snapshots and secrets, state bucket last). Needs: tasks 16, 19. Who: Eng; Human performs and confirms the teardown when wanted.

- **Needs the human:** 1 (decision), 6 (protected-file approval), 7 (one local Docker check), 12 to 14 (apply), 16 (first apply and account), 17 (first deploy), 19 (variables, approval), 20 (teardown). **CI can run:** 2 to 5, 7 to 11, the checks and plan in 15, 18, and the pipeline in 19.

- **Archive when:** the public URL serves the app, `docker compose` (via its `make` target) starts the full system with one command, `terraform plan` on `main` shows no changes after the human's apply, and a push to `main` that passes the tests deploys without manual steps.

## Where SOCBoard differs from vuln-triage
- **One image, not two.** SOCBoard's FastAPI serves the built SPA (spec: one container image), so no nginx container or `/api` proxy; Caddy in front handles TLS only. vuln-triage built a backend and a frontend image. (`frontend/nginx.conf`, `frontend/Dockerfile` there.)
- **One environment in this phase.** vuln-triage ran dev and prod as two Compose projects on one server with a manual prod promotion. SOCBoard defers that to Phase 3.
- **CI plans and applies Terraform.** vuln-triage's CI never applied Terraform (`terraform/README.md`). The ruling asks for CI plan and apply, so SOCBoard adds a plan role, an apply role and an approval gate, and keeps the CI-access module human-applied (CI must not edit its own permissions).
- **Postgres data on the data volume from the start.** vuln-triage left `pgdata` on the root disk (CC33).
- **No placeholder passwords.** vuln-triage's dev deploy fell back to a throwaway database password; SOCBoard fails closed in deployed mode.
- **Health check.** SOCBoard's `/api/health` is database-free by contract; Compose start order uses the Postgres health check.
- **Ingest key and seeded accounts** (SOCBoard-only secrets) join the database password in the Secrets Manager secret.
- **Tag name** `project=socboard`; the IAM tag conditions key on it.
