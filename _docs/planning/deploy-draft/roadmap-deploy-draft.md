# Roadmap 2: Deploy

Order and status only. Acceptance criteria live on the issues; open/closed is read from the tracker. Scope and reasons: `_docs/specs.md` §6 (outline only; see below). Method: `_docs/planning/03_deployment.md` (course material). Readiness check, spec notes and decision questions: `.scratch/deploy-readiness.md` (to become a PM comment).

- **Status:** later (starts when Core ends). **PROVISIONAL:** the spec's Deploy part fails the definition of ready (no journey, no requirements). No issue below is filed until the human approves the spec notes and the first decision. No issue numbers yet.
- **Goal:** The same SOCBoard runs from one container image with Postgres, starts with one Docker Compose command, is covered by integration and end-to-end tests, is reachable at a public URL, and is deployed by CI/CD only when the tests pass.
- **Before any task (not issues):** the human approves the spec notes (Deploy stories, journey 3, boundary and non-goals, invariants, health and bind note) and the spec is committed on its own.
- **Tasks, in order** (proposed issues, one deliverable each). *Needs in Core* is what must be closed first. *Who:* **CI** = GitHub Actions can run it; **Human** = needs the human (account, secrets, Docker on their machine); **Eng** = the Engineer in the sandbox (no Docker, no push).
  1. **Decide the hosting target and deploy method.** Goal: a Heavy decision record choosing the host, the deploy credential and the Postgres location (readiness questions 1, 2, 5). Needs in Core: none. Who: Human decides; PM drafts.
  2. **Serve the built frontend from FastAPI.** Goal: `/` and screen routes return the SPA (`index.html` fallback), `/api/*` unknown paths still give the JSON 404 `not_found`. Needs: #10, #21, #27. Who: Eng; CI tests it.
  3. **Read configuration from the environment.** Goal: database URL, ingest key, seeded-account passwords and poll interval come from env vars, with `.env.example` and a start-up failure in deployed mode when a secret is missing. Needs: #11, #13, #14. Who: Eng; CI.
  4. **Run on Postgres.** Goal: the backend and migrations work on Postgres chosen by the database URL, SQLite stays the local default. Adds a driver dependency (approval first). Needs: #11. Who: Eng; CI with a Postgres service container.
  5. **Prove single ownership on Postgres.** Goal: two simultaneous claims leave exactly one owner, tested on Postgres (spec §5). Needs: #16, task 4. Who: Eng; CI.
  6. **Allow a container to bind a non-loopback address safely.** Goal: the image can listen on `0.0.0.0` through an explicit opt-in while `make backend-run` still refuses any non-loopback host (readiness question 3). Needs: #10, #80. Who: Eng; the human approves the protected-file change.
  7. **Build one container image.** Goal: a multi-stage `Dockerfile` (build frontend, copy `frontend/dist` into the Python image) whose container serves the full app. Needs: #21, #27, tasks 2, 3, 6. Who: Eng writes it; CI builds and starts it (no Docker in the sandbox); Human checks it once on their machine.
  8. **Add the Compose stack.** Goal: `docker-compose.yaml` with the app and Postgres (Postgres health check, app waits for it) and one `make` target that starts the whole system. Needs: #22, tasks 4, 7. Who: Eng writes it; CI or Human runs it.
  9. **Integration tests against the Compose stack.** Goal: the frontend is served, the backend reaches Postgres, login, ingest and queue work through the real stack. Needs: #14, #15, #22, task 8. Who: Eng; CI.
  10. **End-to-end test of both journeys.** Goal: a browser test drives claim, refused second claim, close with a reason and the Lead's audit-trail read, with two analysts and a Lead. Adds a browser-test tool (dependency approval, perhaps a decision record). Needs: #17, #19, #21, #22, task 8. Who: Eng; CI.
  11. **CI builds the image and runs integration and E2E tests.** Goal: on every push and pull request, the workflow runs the tests in parallel, builds the image, then integration and E2E, alongside the existing `make verify`. Needs: tasks 9, 10. Who: Eng writes it; CI is the check; Human pushes.
  12. **First manual deploy to the chosen host.** Goal: the image runs at a public URL with Postgres, seeded users and the ingest key set from secrets, using elevated credentials only while watched. Needs: #22, tasks 1, 7, 8. Who: **Human** (cloud account, secrets, possibly a domain); Eng drafts the infrastructure files and a human task.
  13. **Post-deploy smoke check.** Goal: a `make` target that, given a URL, checks `/api/health`, login, one ingest and that the alert reaches the queue within 5 s. Needs: #14, #15, #13. Who: Eng; CI and Human run it against the public URL.
  14. **Deploy from CI on a green push to `main`.** Goal: the workflow deploys only after tests pass, with a scoped short-lived credential, then runs the smoke check. Needs: tasks 11, 12, 13. Who: **Human** (repository secrets, credential trust set-up); CI runs it.
  15. **Write the deploy and teardown runbook.** Goal: README and `_docs` say how to deploy, where the public URL is, how to get credentials, and how to delete every cloud resource. Needs: tasks 12, 14. Who: Eng; Human performs and confirms the teardown when it is wanted.

- **Needs the human:** 1 (decision), 6 (protected file approval), 12 and 14 (account, secrets, credential trust, possibly a domain), 7 (one local Docker check), 15 (teardown). **CI can run:** 2 to 5, 7 to 11, 13 and the pipeline in 14.
- **Not in this phase:** separate dev and prod, automatic deploy to dev, manual promotion and rollback, metrics, traces, structured logs, alerts and the on-call agent (DevOps, `_docs/planning/04_devops.md`); managed or replicated database, autoscaling, load balancing, high availability; custom domain unless the decision requires it; synthetic alert generator and Lead reassignment (Should-haves); Target Enhancements.
- **Archive when:** the public URL serves the app, `docker compose` (via its `make` target) starts the full system with one command, and a push to `main` that passes the tests deploys without manual steps.
