# Decision: Hand-write `openapi.yaml` as the source of truth for the HTTP API

One file per choice that may be revisited. **Status: approved.** The human approved issue #9, whose `## Decision record` section this file copies, by confirming the body in the session on 2026-11-11 and keeping the `approved` label on the issue (body hash `321acd35ca5e9e01ec02c0615f8547be7523029557e1d4bd84abc7b8215df8c2`, recorded by the PM and matching `make issue-hash N=9`). Heavy tier: an interface other code depends on (the API contract for #10 to #21) and protected files.

- **Decision:** Hand-write `openapi.yaml` from the service layer and the spec before any backend code, version it in the repo root, and treat it as the source of truth that backend tests and the frontend client are checked against. For well-formed requests the refusal order follows the mock (401, 404, 403, 409, 422). For requests that are not well-formed, the tested behaviour applies when authentication is a route dependency: 401 first (if the body parses as JSON), then a case-free role check (`GET /cases`), then the generic 422 `validation_error` before 404, the owner 403, 409 and the domain 422s; unparseable JSON gives 422 even with no token. The domain 422s (`reason_required`, `empty_note`, `invalid_target`) are handler rules after the 409s. The error body is `{ code, message }` with the HTTP status carrying the status; clients ignore unknown properties. Ids are opaque non-empty strings. Concurrent claims: exactly one wins. The reassign target is another analyst only, checked last. The contract is stricter than the mock only for that and for the Lead-only, `status=Closed`-required closed list.
- **Reason:** The service layer already names every call; the contract adds only the rules and error codes the spec requires. A written contract gives each backend issue a checkable target, and lets the real client in #21 be swapped in without guessing. Following the mock's tested order keeps the frontend working unchanged; stating the order that FastAPI was tested to produce means the backend needs no workaround; requiring `code` keeps the client's error handling working; opaque ids and an open error body let the backend change its id scheme or add error fields without breaking clients; the differences from the mock follow the spec and are listed in one place.
- **Alternatives:**
  - *Let FastAPI generate the schema and treat it as the contract:* cheaper, but the contract then follows whatever the first backend issue happens to write.
  - *Let each backend issue define its own endpoints:* fastest at first, drift later.
  - *Change the mock to a 422-before-409 order:* rejected by the human; the mock's order is pinned by tests.
  - *Accept any user as reassign target:* rejected; a Lead is not reassigned work they would be supervising.
  - *Keep `status` in the error body:* rejected; it duplicates the HTTP status.
  - *Run the domain 422s inside schema validation, for example `minLength` on `text`:* rejected; it would put them before the 409s and change the mock's order.
  - *`additionalProperties: false` on `ApiError`:* rejected; it would make every added field a breaking change.
  - *An id `pattern` such as `C-\d+`:* rejected; it would fix the id scheme in the contract.
- **Trade-offs:** A hand-written file can drift from the code; mitigated by tests that compare the backend's generated schema with it. It adds one issue before any backend issue starts. The contract and mock differ in two places (plus the new codes and the malformed-request order) until the frontend work in #21 or a later issue aligns the mock. A schema-invalid request and a domain refusal can both apply to one request; the contract resolves it by saying schema validation comes first. The 401-first rule for malformed requests holds only while authentication stays a route dependency, so #10 carries a constraint. Clients cannot rely on the queue tie order or on which concurrent claim wins.
