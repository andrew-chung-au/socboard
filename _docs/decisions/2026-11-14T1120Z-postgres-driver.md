# Decision: psycopg 3 for Postgres, one migration history with SQLite-only guards, and a Postgres CI job of its own

One file per choice that may be revisited. **Status: proposed** (issue #143, Deploy item D5a; copied from the issue's approved Decision record section, with the two notes marked "(added: ...)"). Only the human sets `approved`.

- **Decision:** use psycopg 3 as the Postgres driver (the `psycopg` package with its `binary` extra, SQLAlchemy dialect `postgresql+psycopg`), added as a runtime dependency. Keep one migration history: migration `0001` creates the SQLite-only objects (the three audit triggers, `sqlite_autoincrement`) only when the dialect is SQLite, and everything else on both. Run Postgres in CI as a service container (Postgres 16) in a workflow file of its own, with throwaway credentials.
  - (added: how the guard is written) The triggers and their drops are guarded by `op.get_context().dialect.name == "sqlite"`. `sqlite_autoincrement` is a SQLite-prefixed table option that SQLAlchemy ignores on other dialects, so it needs no guard; `tests/test_data_migration_dialects.py` shows no AUTOINCREMENT in the Postgres output. The CI image tag is `postgres:16.15` (checked with `docker manifest inspect` at the D0 sitting, PR #179).
  - (added: found by the CI job) On a server database the engine replaces a failed connection with `DatabaseConnectError` and fixed text, with no chained driver error (`socboard/database.py`, a `do_connect` hook on non-SQLite engines only). The first CI run showed the Postgres driver's message (`password authentication failed for user "..."`) in the backend log through the 500 handler's traceback, which criterion 4 of #143 forbids. The SQLite engine and #104's SQLite-only hook in `socboard/sessions.py` are unchanged.
- **Reason:** psycopg 3 is the driver SQLAlchemy 2 supports natively for Postgres, and the kit's dev-container recipe already writes its database URL with `postgresql+psycopg`, so the dev container, CI and the deployment use one URL form. The `binary` extra ships the client library in the wheel, so neither the CI runner nor the image needs a system package. One migration history keeps every database starting from the same file; guards keep the SQLite result identical. A separate workflow file keeps the Postgres job from colliding with other CI changes in the Deploy phase.
- **Alternatives:** psycopg2 (older, in maintenance; a different URL form from the recipe); asyncpg (asynchronous; the app is synchronous); a Postgres-only migration `0002` (allowed as the fallback, but two histories to read); running Postgres tests only in the dev container (not evidence anyone else can see). (added) For the connection message: changing the 500 handler to log class names only (covers every error, but drops detail for all 500s and is outside this issue's files).
- **Trade-offs:** a new runtime dependency with a compiled wheel, so the container image (D10) and the push-check image must be able to install it (`VERIFY:` that a wheel exists for the image's base; the CI runner and the push-check image installed it on 2026-11-14); the guards make migration `0001` dialect-dependent, so its tests cover both; the CI job adds minutes to every pull request. (added) A failed Postgres connection now logs only fixed text, so the cause (wrong password, missing database, host down) is not in the app log; the Postgres server's own log still has it. The append-only rule is not on Postgres until D6a.
- **Evidence:** `_docs/specs.md` sections 4 (Deploy stories) and 6; the Deploy decision record `_docs/decisions/2026-11-13T2156Z-deploy.md` (Postgres 16, decision 4, part E); `_docs/agent-kit/environments/local-sandbox/compose/devcontainer.json` (`postgresql+psycopg` URL); `socboard/database.py`, `socboard/migrate.py`, `socboard/sessions.py`; `_docs/planning/deploy-backlog-proposal.md` (D5a); CI runs of the `socboard postgres` workflow on the #143 branch.
