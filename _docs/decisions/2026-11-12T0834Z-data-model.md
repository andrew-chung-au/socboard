# Decision: SQLAlchemy 2.x models and Alembic migrations, with one conditional UPDATE for single ownership

One file per choice that may be revisited. **Status: approved.** Note (#99): the Trade-offs bullet now lists the guard's remaining limits and records how explicit audit ids are refused (decision approved with issue #99, body hash `a6186015b0e8221a5334e087c65af41f8c07d8aead0a133d87cc8906ab2fa910`). The human approved issue #11, whose `## Decision record` section this file copies, by confirming the body in the session on 2026-11-12, and ruled the append-only design (option B, database triggers) on the same day, with the `approved` label on the issue (body hash `2d1616055ca0c8e47a295ee8842e494a01674cf970fa436b9d98746ca0c6015e`, matching `make issue-hash N=11`). Heavy tier: the schema is an interface every later issue depends on, it carries the one-owner and append-only rules, and it adds dependencies and touches protected files.

- **Decision:** Use SQLAlchemy 2.x models with Alembic migrations, SQLite for Core. Table names are plural. Primary keys are database-assigned integers, exposed as decimal strings through one helper pair (`to_public_id`, `from_public_id`), as decided by the human. Enumerated values are constrained strings (named CHECK constraints) built from one list that a test compares with `openapi.yaml`. The closing reason is guarded by two database CHECK constraints (reason present if and only if the status is Closed), as decided by the human; the choosing logic and the 422 `reason_required` stay with #17. The database URL is read from `SOCBOARD_DATABASE_URL`, as decided by the human. Timestamps use one UTC-only column type. One function, `append_audit`, writes audit entries inside the caller's transaction. The audit trail is append-only in the database: triggers on `audit_entries` refuse any UPDATE, any DELETE and any INSERT that reuses an id, and a named CHECK `id >= 1` on `audit_entries` (`ck_audit_entries_id_positive`) keeps the id-reuse trigger usable: SQLite gives `NEW.id` the value -1 when no id is supplied (tested on SQLite 3.46.1 and 3.40.0), so the trigger tests only whether a row with `id = NEW.id` exists, and without the CHECK one row with id -1 would make every later plain insert, and so every `append_audit`, fail; the id rule for the other tables is unchanged; an application-layer guard refuses DDL on the table and repeats the UPDATE and DELETE checks as a second layer. The human ruled this (option B) on 2026-11-12. **Single ownership** is enforced by one conditional UPDATE and one nullable column. The owner is `cases.owner_id`, one nullable foreign key; the human decided to drop the assignment table, so there is none, and assignment history is the `claimed` and `reassigned` audit entries. A claim is the statement `UPDATE cases SET owner_id = :user_id WHERE id = :case_id AND owner_id IS NULL AND status <> 'Closed'`, executed once in the claimant's transaction. One row changed means the claim won; no row changed means it lost, and only then does the code read the case to choose between 404 `not_found`, 409 `case_closed` and 409 `already_claimed`. The code never reads the owner first and then writes. The `claimed` audit entry is appended in the same transaction only after the row count is 1. #16 implements this and tests concurrent claims.
- **Reason:** The spec says exactly one of two simultaneous claims wins on any supported database. A single conditional UPDATE is atomic on SQLite and on Postgres and cannot leave two owners because there is only one owner column. It needs no application lock. On Postgres it needs no retry at READ COMMITTED (the second statement waits, re-checks `owner_id IS NULL` and changes no row); at REPEATABLE READ or SERIALIZABLE the loser gets a serialization failure, so the application runs at READ COMMITTED. On SQLite the loser waits for the write lock and gets `database is locked` if the winner's transaction outlasts the busy timeout, or at once if its own transaction read before the claim under a real `BEGIN`; #11 keeps the driver's default transaction mode and a 5 s busy timeout (both tested clean), never `BEGIN IMMEDIATE`, and #16 decides what a lock timeout answers. A read-then-write check, or a second table holding assignments, allows a window or a disagreement between two records of the owner. Alembic is the standard migration tool for SQLAlchemy and gives a reviewable history. Constrained strings behave the same on SQLite and Postgres. Integer keys give a stable "as stored" order for audit entries and notes. One audit function is simple to test. Append-only is enforced in the database because an application guard that lists constructs missed ordinary SQLAlchemy forms in three independent reviews (aliases and case variants, then `lambda_stmt` and `table()`); only the database sees every write, whatever form it was built in, and the spec makes the audit trail append-only.
- **Alternatives:** A read-then-write claim inside a transaction (needs `SELECT ... FOR UPDATE`, which SQLite lacks); a version column with retry (more code for the same result); an assignment table as the owner of record (two sources of truth); opaque string keys such as UUIDs (no insertion order for audit entries without a second column); hand-written SQL migrations (no new dependency, easy to get wrong); database enum types (Postgres-only features); an application-layer guard only (the earlier choice; ordinary constructs such as aliases, case-variant names, `lambda_stmt` and `table()` got past it); record the gaps as accepted (honest but weak for a SOC audit trail).
- **Trade-offs:** What can still bypass it: raw-SQL DDL and DML sent through `text()`, `exec_driver_sql` or a DBAPI cursor, and direct access to the database file. That includes `DROP TRIGGER`, a raw `UPDATE sqlite_sequence`, and `PRAGMA ignore_check_constraints` and `PRAGMA writable_schema` sent as raw SQL; the application guard refuses the same things only when they are built with SQLAlchemy constructs (and, for DDL outside `socboard/migrate.py`, as `DDL(...)`). The guard is not a SQL parser: it matches the rendered text of a `DDL(...)` (after its `context` substitution) as whole words, and the table and index names of SQLAlchemy constructs. All of these are deliberate acts, not accidental routes. **Closed by #99, in the guard:** it refuses an INSERT into `audit_entries` that supplies a non-NULL `id` (the id is database-assigned and `append_audit` never supplies one), `DropIndex` of the table's index, `PRAGMA ignore_check_constraints` and `PRAGMA writable_schema` as `DDL`, and writes to `sqlite_sequence` made with SQLAlchemy constructs. An upper bound on the `id` CHECK was not used: a row allowed at the bound makes the next automatic id exceed it, so `append_audit` fails at the bound instead of at 2^63-1, and a bound needs a migration that rebuilds `audit_entries`. **De-duplication:** `INSERT OR IGNORE` and `ON CONFLICT DO NOTHING` on an existing audit id raise (the trigger `audit_entries_no_reuse_id`, or the guard when the id is explicit) instead of skipping, so #14 and later issues must not de-duplicate audit entries that way. A migration that inserts audit rows with explicit ids through SQLAlchemy constructs is refused, because `allow_schema_changes()` lifts only the DDL check; it must use raw SQL or change the guard with a new record. Postgres needs equivalent triggers, added in the Deploy phase with the Postgres migration. Alembic and SQLAlchemy are new dependencies and need the human's approval. Enforcing "reason only when Closed" in the database makes #17 set status and reason in one statement; that is what it must do anyway. Alembic's autogenerate does not see CHECK constraints or triggers, so the tests insert bad values into the migrated database and compare the trigger text in `sqlite_master`. A later migration that rebuilds `audit_entries` (Alembic batch mode on SQLite) silently drops the three triggers and `AUTOINCREMENT`. Such a migration must re-create the triggers from literals in its own file and pass `table_kwargs={"sqlite_autoincrement": True}`; the tests that expect the three triggers and `AUTOINCREMENT` after `upgrade head` fail if it does not. The trigger SQL is SQLite's and is written again for Postgres.
