# Decision: SQLAlchemy 2.x models and Alembic migrations, with one conditional UPDATE for single ownership

One file per choice that may be revisited. **Status: approved.** The human approved issue #11, whose `## Decision record` section this file copies, by confirming the body in the session on 2026-11-12 (and re-reading the section after the F1 and F3 changes), with the `approved` label on the issue (body hash `1166243ee4c0c1ae8a01ece961d98faf755916131927f3eedf026cd0ad667f7f`, recorded by the PM and matching `make issue-hash N=11`). Heavy tier: the schema is an interface every later issue depends on, it carries the one-owner and append-only rules, and it adds dependencies and touches protected files.

- **Decision:** Use SQLAlchemy 2.x models with Alembic migrations, SQLite for Core. Table names are plural. Primary keys are database-assigned integers, exposed as decimal strings through one helper pair (`to_public_id`, `from_public_id`), as decided by the human. Enumerated values are constrained strings (named CHECK constraints) built from one list that a test compares with `openapi.yaml`. The closing reason is guarded by two database CHECK constraints (reason present if and only if the status is Closed), as decided by the human; the choosing logic and the 422 `reason_required` stay with #17. The database URL is read from `SOCBOARD_DATABASE_URL`, as decided by the human. Timestamps use one UTC-only column type. The audit trail is append-only at the application layer: one function, `append_audit`, writes entries inside the caller's transaction, and the ORM refuses to update or delete one (mapper events, a `do_orm_execute` hook and one engine `before_execute` listener that refuse any UPDATE or DELETE on `audit_entries`), with no database triggers in Core. **Single ownership** is enforced by one conditional UPDATE and one nullable column. The owner is `cases.owner_id`, one nullable foreign key; the human decided to drop the assignment table, so there is none, and assignment history is the `claimed` and `reassigned` audit entries. A claim is the statement `UPDATE cases SET owner_id = :user_id WHERE id = :case_id AND owner_id IS NULL AND status <> 'Closed'`, executed once in the claimant's transaction. One row changed means the claim won; no row changed means it lost, and only then does the code read the case to choose between 404 `not_found`, 409 `case_closed` and 409 `already_claimed`. The code never reads the owner first and then writes. The `claimed` audit entry is appended in the same transaction only after the row count is 1. #16 implements this and tests concurrent claims.
- **Reason:** The spec says exactly one of two simultaneous claims wins on any supported database. A single conditional UPDATE is atomic on SQLite and on Postgres and cannot leave two owners because there is only one owner column. It needs no application lock. On Postgres it needs no retry at READ COMMITTED (the second statement waits, re-checks `owner_id IS NULL` and changes no row); at REPEATABLE READ or SERIALIZABLE the loser gets a serialization failure, so the application runs at READ COMMITTED. On SQLite the loser waits for the write lock and gets `database is locked` if the winner's transaction outlasts the busy timeout, or at once if its own transaction read before the claim under a real `BEGIN`; #11 keeps the driver's default transaction mode and a 5 s busy timeout (both tested clean), never `BEGIN IMMEDIATE`, and #16 decides what a lock timeout answers. A read-then-write check, or a second table holding assignments, allows a window or a disagreement between two records of the owner. Alembic is the standard migration tool for SQLAlchemy and gives a reviewable history. Constrained strings behave the same on SQLite and Postgres. Integer keys give a stable "as stored" order for audit entries and notes. One audit function is simple to test, and triggers differ between SQLite and Postgres.
- **Alternatives:** A read-then-write claim inside a transaction (needs `SELECT ... FOR UPDATE`, which SQLite lacks); a version column with retry (more code for the same result); an assignment table as the owner of record (two sources of truth); opaque string keys such as UUIDs (no insertion order for audit entries without a second column); hand-written SQL migrations (no new dependency, easy to get wrong); database enum types (Postgres-only features); database triggers for append-only (stronger, written twice and tested on a database not available until Deploy).
- **Trade-offs:** Application-layer append-only can be bypassed only by `text()` (raw SQL) and by direct access to the database file; accepted for Core and revisited in the Deploy phase. Alembic and SQLAlchemy are new dependencies and need the human's approval. Enforcing "reason only when Closed" in the database makes #17 set status and reason in one statement; that is what it must do anyway. Alembic's autogenerate does not see CHECK constraints, so the tests insert bad values into the migrated database.
