# Decision: Signed stateless bearer tokens and scrypt password hashes, standard library only

One file per choice that may be revisited. **Status: approved.** The human approved issue #13, whose `## Decision record` section this file copies, with the `approved` label on the issue (body hash `a0b0f61c4b82159f4bb41611e5caf10ddff255fc7ad93c3af58a7b6169bfff07`, matching `make issue-hash N=13`), and in the session on 2026-11-12 re-read and confirmed that section as is. The 8-hour lifetime is the human's ruling. Heavy tier: an authentication boundary and the app's session wiring.

- **Decision:** Signed stateless bearer tokens (HMAC-SHA256 over the user's public id and an expiry, standard library only) with a fixed lifetime of 8 hours, and password hashes made with scrypt from the standard library, stored as one self-describing string with a per-password random salt. The role is read from the database on each request, not from the token. Seed passwords come from environment variables, not code; the signing secret comes from `SOCBOARD_TOKEN_SECRET` and the app refuses to start without it.
- **Reason:** Meets "hashed passwords, bearer token" (spec section 2) with no new dependency and no extra table. Seed passwords in the environment keeps plaintext out of the repo. Reading the role from the database makes a removed user or a changed role effective at once, which a stateless token alone cannot. Eight hours covers one analyst shift, and the frontend already handles a 401 by asking the user to sign in again (contract message "Your session has expired. Please sign in again.").
- **Alternatives:** JWT through a library (familiar, adds a dependency and its option surface); opaque tokens stored in a table (supports revocation, needs a table and lookups on every request); seeded demo passwords in code (convenient, but breaks the no-plaintext rule); a shorter lifetime such as 1 hour (safer, but forces a mid-shift login with no refresh endpoint); a longer one such as 24 hours (fewer logins, longer exposure of a stolen token).
- **Trade-offs:** No revocation until expiry, accepted because logout and revocation are out of scope. Demo set-up needs four variables set once (the secret and three passwords). The standard-library token code is small but must be tested well. `hashlib.scrypt` needs OpenSSL scrypt support; the first test confirms it in the dev container and in CI.
- **Evidence:** `_docs/specs.md` section 2; `openapi.yaml` (`login`, `listUsers`, `LoginRequest`, `LoginResponse`, `User`, the refusals table and the order of checks); `_docs/decisions/2026-11-11T1511Z-openapi-contract.md`; `_docs/planning/02_development-example.md` auth pattern; spec section 5 (no credentials in telemetry).

## As built (#13)

- **Token lifetime:** 8 hours, `TOKEN_LIFETIME_SECONDS = 28800` in `socboard/tokens.py`; a fixed constant, not read from the environment. A token is refused at or past its `exp`. The reader also refuses a token whose `exp` is more than the lifetime ahead of the current time, using integer arithmetic only, so a correctly signed token cannot outlive 8 hours.
- **Token format:** `<payload>.<signature>`, both base64url without padding. The payload is the JSON object `{"exp": <int>, "sub": "<public id>"}`; the signature is HMAC-SHA256 over the payload text as sent, compared with `hmac.compare_digest` before the payload is decoded. Tokens longer than 1024 characters are refused before any work.
- **scrypt parameters:** N = 2^17 (131072), r = 8, p = 1 (about 128 MiB per hash): the first of the minimum sets in the OWASP password storage guidance. Salt 16 random bytes per password (`secrets.token_bytes`), derived key 32 bytes, compared with `hmac.compare_digest`. Stored as `scrypt$n=131072,r=8,p=1$<salt>$<hash>` in `users.password_hash`, so the cost can be raised later; `verify_password` reads the parameters from the stored string. The parameters read back from a stored hash are bounded (#104): N up to 2^18, r up to 8, p up to 2, and memory (128 * N * r * p) up to 2^28 bytes (256 MiB); anything above verifies as False after the dummy-hash work. Measured in the dev container (OpenSSL 3.5.7): about 0.32 s per hash.
- **Unknown username:** login verifies the submitted password against a fixed dummy hash made with the same parameters (`passwords.DUMMY_HASH`), so it does the same work as a wrong password and returns the same 401 `invalid_credentials` body.
- **Minimums:** the signing secret is at least 32 characters after leading and trailing whitespace is trimmed (#104; the value is used as given, not trimmed); each seed password at least 12.
