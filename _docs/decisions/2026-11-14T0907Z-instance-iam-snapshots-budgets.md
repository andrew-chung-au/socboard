# Decision: The instance role, the daily snapshot schedule and the budgets are a human-applied Terraform part

One file per choice that may be revisited. **Status: approved** by the human on 2026-11-14 in the orchestrator session ("decision approved"), set by the orchestrator in the human's name. Heavy tier: it defines the server's IAM permissions (spec section 5). It applies decision 10 of the Deploy decision record (`2026-11-13T2156Z-deploy.md`, issue #139) and adds no new rule beyond these choices. Issue #162 (D17a); body hash `32bbb006d38e7b3df56d17bb92bd1baaab6dc0ae582698ab16730198ad5742a7`. The AWS details are unchecked until the human's first apply (`VERIFY:` comments in `terraform/iam-and-budgets/main.tf`).

- **Decision:** `terraform/iam-and-budgets/` holds, applied only by the human: the instance role (trust names only `ec2.amazonaws.com`) with the AWS-managed Systems Manager core policy plus one inline statement allowing `secretsmanager:GetSecretValue` on exactly one secret ARN (a variable); the instance profile (its name is the output D17b reads); an Amazon Data Lifecycle Manager policy that snapshots every volume tagged `project=socboard` daily and keeps the 7 newest, with its execution role (trust names only `dlm.amazonaws.com`, AWS-managed `AWSDataLifecycleManagerServiceRole` policy); and one monthly cost budget with notifications at 50, 80 and 100 percent of actual spend to an address the human sets. The amount, the address and the secret ARN are set in an ignored variable file. No data source reads a secret.
- **Reason:** decision 10 keeps every IAM resource in the human-applied part so CI cannot widen its own reach. A managed policy avoids hand-writing the agent's permission list; the one inline statement keeps secret access to one ARN. The schedule and its role sit here, so the CI-applied part needs no permission to pass a second role and decision 10's one-role limit holds. DLM is the smallest snapshot service that works: one policy and one role, selecting volumes by tag, so it can be applied before the volume exists.
- **Alternatives:** a hand-written Systems Manager policy (narrower, but must track the agent's changing needs); AWS Backup (a vault and a plan for the same result); the schedule in the CI-applied part (needs a pass-role permission decision 10 does not allow); DLM's default service-linked role instead of an execution role (`VERIFY:` whether the provider argument `execution_role_arn` is optional; it is created here so the trust and permissions are visible in code).
- **Trade-offs:** the managed policy may grant more than the agent needs (`VERIFY:` at the first apply); every later change to the instance's permissions, the schedule or the retention is a manual apply by the human; the schedule acts on every volume carrying `project=socboard`, so the tag must be unique to this deployment (a root volume tagged the same way is snapshotted too); the snapshot role's AWS-managed policy is probably account-wide with no tag condition, so the role can likely act on any volume or snapshot in the account and the tag only chooses what the schedule snapshots (`VERIFY:` against the policy's current document at the first apply; it is not replaced by an inline policy here); the retention of 7 and the 03:00 UTC time are fixed in code, not variables; snapshots already taken outlive a destroy of the schedule. **Rule for D17b:** the server part's root volume must not carry the tag `project=socboard` (or the human accepts the extra snapshots knowingly), and D17b's issue must carry that as a criterion. **For #156 (D16):** the CI apply role's deny must cover `iam:*` (including the roles `socboard-instance` and `socboard-snapshot`), `dlm:*` (the snapshot policy), `budgets:*` (the budget) and, if CI holds EC2 rights, `ec2:DeleteSnapshot`, so CI cannot shorten retention or change the budget address.
