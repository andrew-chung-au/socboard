# Decision: Run the frontend tests in `make test` and `make verify`

One file per choice that may be revisited. **Status: approved.** The human approved issue #46, whose `## Decision record` section this file copies, by adding the `approved` label on 2026-11-11 (hash `c8db0ddedc3f9aaad6606930751fb84bd7e71765652c77c4a3c33770544f218e`). Heavy tier: it changes what `make test` and `make verify` run for every later issue and touches CI and the push-check image.

- **Decision:** `make install` installs the frontend packages and `make test` runs the frontend tests (Vitest, through `make frontend-test`) after pytest, so `make verify`, CI and the push check all run them. bun 1.4.2 and Node 24.22.0 are added to CI and to the push-check image, `TEST_FILES` covers `frontend/src/test/*` and `*vitest.config.*`, and a run with no `frontend/node_modules` fails instead of skipping.
- **Reason:** #8 adds many frontend tests that must gate every later issue. The gate is `TEST_CMD="make test"`; a test the gate does not run protects nothing, and a skipped run would let a green `make verify` mean "frontend not tested". One command (`make test`) staying "all tests" keeps `AGENTS.md` and the verification procedure true.
- **Alternatives:**
  - *Keep the frontend tests out of `make test`* (run only `make frontend-test` by hand or as a separate CI step): rejected by the human on 2026-11-10. `make verify` and the push check would not see frontend regressions, and each later issue would depend on someone remembering a second command.
  - *Add the frontend tests to `TEST_CMD` only* (`TEST_CMD="make test frontend-test"`): same effect on `make verify`, but `make test` would no longer mean all tests, and the pre-push and CI paths that call `make test` directly would diverge.
  - *Skip the frontend tests with a warning when `frontend/node_modules` is missing:* lets environments without bun or the registry stay green, but a green gate would no longer mean the frontend ran; rejected for that reason.
  - *Put these edits inside #8:* rejected on 2026-11-10; one intent per issue, and #8 then needs no protected commit.
- **Trade-offs:** Every place that runs the gate needs bun, Node and the npm registry (dev container, CI, the push-check image; Kiro Web may not have the registry, so Engineer and QA runs there cannot produce a green `make verify` and the human verifies instead). A fresh dev container needs `make install` once before the pre-push hook passes. The gate is slower. The protected surface grows by six files, each approved separately, and the image must be rebuilt by the human. Pins and action majors are unverified until the first build and CI run. Vitest markers that `verify.sh` does not match (`.skipIf(`, `.runIf(`, `it.fails(`, `xtest(`, `fit(`, `fdescribe(`) stay a gap until an upstream change.
- **Evidence:** Issue #46 (this decision; the human's rulings on its four decision questions are in its comments); #8 (the dependent issue); #27 (`frontend-install`, `frontend-build`, bun in `.devcontainer/setup.sh`); `agent-kit.conf` `TEST_CMD`; `_docs/agent-kit/scripts/verify.sh`.
