- **Decision:** The Deploy phase follows the ten decisions, the region, the accepted risks, the pin and the never-hold rules below.

  **A. The seven decisions of 2026-11-12 (human), reproduced from the roadmap; wording added from `_docs/planning/deploy-backlog-proposal.md` is marked "(added: ...)" in items 3 and 5, and the cross-reference "Amended by decision 10 below" in item 2 is also added wording**
  1. **Terraform on AWS**, one environment, one server. Infrastructure as code makes the environment repeatable.
  2. **CI and Terraform.** Pull requests run `fmt`, `validate` and a read-only `plan`. `apply` runs from CI only for the server part, only on `main`, in an `infra` GitHub Environment where a named reviewer must approve and administrators are not exempt. The state bucket and the CI-access part are applied only by the human, so CI cannot widen its own permissions. **Amended by decision 10 below.**
  3. **Bind address.** `make backend-run` stays loopback-only. The image sets an explicit opt-in (added: a command-line flag, not an inherited variable); without it `SOCBOARD_HOST=0.0.0.0` still exits with an error, and a test covers the refusal. The app port is published on the host's loopback only, behind Caddy.
  4. **Postgres** runs as a container beside the app, with its files on the encrypted data volume and daily snapshots. A restore note goes in the runbook. A managed database (RDS) is the Phase 3 upgrade.
  5. **Secrets.** The ingest key, the seeded passwords and the database password live in one Secrets Manager secret the human creates. In deployed mode the app refuses to start if one is missing. The human hands reviewers their credentials out of band, not in the README. (added: Spec note A, pending the human, adds the token signing secret to this list.)
  6. **URL and TLS.** A hostname derived from the server's Elastic IP through a public wildcard-DNS service, with Caddy issuing the certificate automatically (a real contact address or none). While testing, use the certificate authority's staging endpoint or another wildcard-DNS service to stay under rate limits.
  7. **Cost.** No stop schedule in this phase. Budget notifications at half, 80 percent and the full limit; `terraform destroy` when idle. Revisit in Phase 3.

  **B. The three new decisions (the human approved the issue's Decision record section on 2026-11-13; this file stays `proposed` until the human sets `approved`)**
  8. **Audit trail on Postgres.** The migration creates, on Postgres, row-level BEFORE UPDATE and BEFORE DELETE triggers that raise an error, a BEFORE INSERT trigger that refuses a duplicate id, and a statement-level BEFORE TRUNCATE trigger (a truncate does not fire row triggers). The application connects as a role that does not own the table and cannot disable triggers or run DDL; migrations run as the owner role. A role with no UPDATE or DELETE privilege on `audit_entries` is recorded as a Phase 3 hardening. **What the database owner can still do:** the table owner and any superuser can disable or drop the triggers, run DDL on the table, or truncate it after disabling them. The triggers protect against the application role, a bug in application code and raw SQL sent as that role; they do not protect against the owner. D6a (not filed yet) builds the Postgres triggers and their tests. (added, VERIFY: against the Postgres documentation) Postgres triggers do not fire when `session_replication_role` is `replica`. The application-layer guard (the data-model record, `2026-11-12T0834Z-data-model.md`) stays as an extra layer; its Postgres review is D6b (not filed yet), after #107.
  9. **Limits.** Login and ingest limits are counted in the process, with one worker (the start command pins one worker), and reset when the process restarts. They are not shared between replicas. **Known limit:** a restart clears the counters, and a second worker or replica would multiply the allowed attempts. The numbers (attempts, window, ingest rate) and how the client address is read behind Caddy are chosen in the D8 (login) and D9 (ingest) issues (not filed yet), which own the defaults. This record chooses none.
  10. **Amendment to decision 2 (human, 2026-11-13).** "Apply from CI only for the server part" now excludes **every IAM resource and the budgets**. The instance role and instance profile, any role the snapshot schedule needs (`VERIFY:` whether one is needed), and the budgets (instance IAM and budgets are D17a, #162) are applied only by the human, together with the CI-access part (D16, #156). The CI apply role may only attach that one named role to the instance, and has an explicit deny on other IAM writes (`VERIFY:` the exact permission; unverified until the first apply). The daily snapshot schedule and any execution role it needs are both in the human-applied part (#162, D17a); the schedule selects the data volume by its `project=socboard` tag. The CI-applied server part (D17b, not filed yet) creates the volume and no schedule or role. **Cost:** any later change to the instance's permissions is a manual apply by the human.

  **C. Region (human, 2026-11-13; this wording follows the human's later clarification, not the older issue wording)**
  - The deployment runs in `us-east-1`. It is the human's own AWS account, whose home region is `ap-southeast-2`. The human has used `us-east-1` before, so no organisation policy is expected to block it; nothing here checks that.
  - **Follow the region (`us-east-1`):** every regional resource (the server, the data volume, the snapshots, the Secrets Manager secret) is in `us-east-1`, and the Terraform state bucket is in `us-east-1` unless the human picks otherwise; that choice is the human's, and nothing in this record makes it.
  - **Global:** IAM, the GitHub OIDC provider and the roles.
  - **Account-wide:** budget notifications.
  - Nothing here is verified against AWS before the human's first apply (`VERIFY:` each AWS-specific detail in the Terraform issues).

  **D. Accepted risks**
  - Single server, no high availability: a server fault is an outage until the human re-applies or restores.
  - Postgres on the same host as the app: one host fault takes both, and the daily snapshot is the only backup (RDS is the Phase 3 upgrade).
  - A public URL on a shared wildcard-DNS name. (added: certificate rate limits, which decision 6 mentions, and the name's availability depend on a third party.)
  - Reviewers in Australia reach a US-east server: this adds latency but not a correctness risk against the 5 second target (spec §5); the smoke check (D21, not filed yet) measures it.
  - The limits of decision 8 (the owner can disable the triggers) and decision 9 (counters reset on restart).
  - The first real check of every AWS detail is the human's first apply.

  **Note on issue #141 (D3), which is not an enforcement of any row above.** Its start-up refusal makes the app require its own secrets when it starts in deployed mode: a missing, empty or too-short token signing secret, ingest key or database URL stops it with exit 2 (criterion 2 of #141). It does not look at the repository, the image, Terraform outputs or the bundle. The three seeded passwords are not covered by it: the app never reads them, and only the one-shot seed step requires them (`make seed` already refuses a missing or short one). The database password has no check of its own; #141 checks the database URL as a whole. A long-lived cloud key is outside it.

  Rows with no check today: the image, Terraform state and its outputs, and GitHub secrets. The repository row has only the file-name check at commit, run locally, and no check of file contents. The frontend bundle row has only the partial `make frontend-build` check, which nothing runs automatically. No planned check above exists yet: some are filed as issues (#154, #156, #162) and the rest are not filed yet, so each is a requirement and not a coverage. This record says so rather than claiming a check.

- **Reason:**
  1. (Decision 8) Spec §5 says the audit trail is append-only: entries are never edited or deleted ("on any supported database" is spec §5's wording for the one-owner rule, not for this one), and the database is the layer that holds even if application code is wrong; the SQLite rule is the same shape (three triggers, plus truncate on Postgres).
  2. (Decision 9) One server and one container make shared counters unnecessary, and in-process counters are the smallest change.
  3. (Decision 10) An apply role that can write IAM could widen its own reach, which spec §5 forbids.
  4. (Region) The human's ruling of 2026-11-13, given in the session and recorded in `_docs/planning/deploy-backlog-proposal.md` (the "Human ruling, 2026-11-13" note at the top, and section 5 item D19) and in the revision note of `_docs/planning/roadmap-3-deploy.md`.
  5. (Pin) One major version is used in the dev container, the CI service and the Compose stack (the issue's criterion). Source: the human's ruling of 2026-11-13, recorded in the same Orchestrator comment on #139; the kit's Compose recipe uses a 16.x image.
  6. (Never-hold table) The issue requires each rule to name the later issue and check that enforces it, so that no rule is left to review alone. The table also says which checks exist today and which do not, so it claims no check that is absent.
- **Alternatives:**
  1. (Decision 8) Privileges only, no triggers: protects against the application role but not against the owner, and gives no truncate or overwrite refusal on its own; both together are the Phase 3 hardening. Guard in application code only: one layer, refuses nothing sent as raw SQL.
  2. (Decision 9) Counters in the database: survive restarts, but more code and more writes per request.
  3. (Decision 10) Keep the instance role in the CI-applied part: simpler, but breaks spec §5.
  4. (Region) (added) `ap-southeast-2`, the account's home region: not chosen; the human ruled `us-east-1`.
  5. (Pin) (added) Another major version: the issue lets the human name one when approving; the human confirmed 16.
- **Trade-offs:**
  1. (Decision 8) A superuser or the table owner can still disable the triggers (stated above). Two database roles must be created in Compose and in production. Postgres trigger syntax differs from SQLite, so the two rules are kept in step by tests on both.
  2. (Decision 9) Limits reset on restart, and a second worker or replica would multiply them; the start command pins one worker.
  3. (Decision 10) Any later change to the instance's permissions is a manual apply by the human.
  4. (Region) Latency for reviewers in Australia (see the accepted risks).
  5. (Pin) The tag must be checked at the dev-container sitting; until then it is unverified.
  6. The record states rules whose checks (D10, not filed yet; D16 as #156; and the Terraform items, some filed and some not) are not built yet, and several rules have no check today (see the table in part F); the rules are stated now, and their checks follow when the named items are built or filed.
