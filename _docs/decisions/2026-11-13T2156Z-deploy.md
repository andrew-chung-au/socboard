# Decision: The Deploy phase rules: Terraform on AWS, one server, Postgres 16, and what the cloud, the image and CI must never hold

One file per choice that may be revisited. **Status: proposed.** Only the human sets `approved`. The human ruled the seven decisions of 2026-11-12 (copied here from `_docs/planning/roadmap-3-deploy.md`, not re-decided) and approved the `## Decision record` section of issue #139 on 2026-11-13, including Postgres 16 (body hash `3ec233a6e7d88f8deb48c1baa822390deb7c232aa40e20aaef98c928ab946534`, matching `make issue-hash N=139`). Heavy tier: it fixes the rules the whole Deploy phase follows, including a security-boundary decision (the audit trail on Postgres). Later Deploy issues (D-labels, defined in `_docs/planning/deploy-backlog-proposal.md`) cite this record.

- **Decision:** The Deploy phase follows the ten decisions, the region, the accepted risks, the pin and the never-hold rules below.

  **A. The seven decisions of 2026-11-12 (human), as the roadmap states them**
  1. **Terraform on AWS**, one environment, one server. Infrastructure as code makes the environment repeatable.
  2. **CI and Terraform.** Pull requests run `fmt`, `validate` and a read-only `plan`. `apply` runs from CI only for the server part, only on `main`, in an `infra` GitHub Environment where a named reviewer must approve and administrators are not exempt. The state bucket and the CI-access part are applied only by the human, so CI cannot widen its own permissions. **Amended by decision 10 below.**
  3. **Bind address.** `make backend-run` stays loopback-only. The image sets an explicit opt-in (a command-line flag, not an inherited variable); without it `SOCBOARD_HOST=0.0.0.0` still exits with an error, and a test covers the refusal. The app port is published on the host's loopback only, behind Caddy.
  4. **Postgres** runs as a container beside the app, with its files on the encrypted data volume and daily snapshots. A restore note goes in the runbook. A managed database (RDS) is the Phase 3 upgrade.
  5. **Secrets.** The ingest key, the seeded passwords and the database password live in one Secrets Manager secret the human creates. In deployed mode the app refuses to start if one is missing. The human hands reviewers their credentials out of band, not in the README. (Spec note A, pending the human, adds the token signing secret to this list.)
  6. **URL and TLS.** A hostname derived from the server's Elastic IP through a public wildcard-DNS service, with Caddy issuing the certificate automatically (a real contact address or none). While testing, use the certificate authority's staging endpoint or another wildcard-DNS service to stay under rate limits.
  7. **Cost.** No stop schedule in this phase. Budget notifications at half, 80 percent and the full limit; `terraform destroy` when idle. Revisit in Phase 3.

  **B. The three new decisions (approved with issue #139)**
  8. **Audit trail on Postgres.** The migration creates, on Postgres, row-level BEFORE UPDATE and BEFORE DELETE triggers that raise an error, a BEFORE INSERT trigger that refuses a duplicate id, and a statement-level BEFORE TRUNCATE trigger (a truncate does not fire row triggers). The application connects as a role that does not own the table and cannot disable triggers or run DDL; migrations run as the owner role. A role with no UPDATE or DELETE privilege on `audit_entries` is recorded as a Phase 3 hardening. **What the database owner can still do:** the table owner and any superuser can disable or drop the triggers, run DDL on the table, or truncate it after disabling them. The triggers protect against the application role, a bug in application code and raw SQL sent as that role; they do not protect against the owner. The application-layer guard (the data-model record, `2026-11-12T0834Z-data-model.md`) stays as a second layer and is the only layer that refuses DDL sent through the application; its review is D6b, after #107.
  9. **Limits.** Login and ingest limits are counted in the process, with one worker (the start command pins one worker), and reset when the process restarts. They are not shared between replicas. **Known limit:** a restart clears the counters, and a second worker or replica would multiply the allowed attempts. The numbers (attempts, window, ingest rate) and how the client address is read behind Caddy are chosen in the D8 (login) and D9 (ingest) issues, which own the defaults. This record chooses none.
  10. **Amendment to decision 2 (human, 2026-11-13).** "Apply from CI only for the server part" now excludes **every IAM resource and the budgets**. The instance role and instance profile, any role the snapshot schedule needs (`VERIFY:` whether one is needed), and the budgets are applied only by the human, together with the CI-access part (D17a). The CI apply role may only attach that one named role to the instance, and has an explicit deny on other IAM writes (`VERIFY:` the exact permission; unverified until the first apply). **Cost:** any later change to the instance's permissions is a manual apply by the human.

  **C. Region (human, 2026-11-13; this wording follows the human's later clarification, not the older issue wording)**
  - The deployment runs in `us-east-1`. It is the human's own AWS account, whose home region is `ap-southeast-2`. The human has used `us-east-1` before, so no organisation-policy check is needed (nothing to verify there).
  - **Follow the region (`us-east-1`):** every regional resource: the server, the data volume, the snapshots, the Secrets Manager secret, and the Terraform state bucket unless the human picks otherwise.
  - **Global:** IAM, the GitHub OIDC provider and the roles.
  - **Account-wide:** budget notifications.
  - Nothing here is verified against AWS before the human's first apply (`VERIFY:` each AWS-specific detail in the Terraform issues).

  **D. Accepted risks**
  - Single server, no high availability: a server fault is an outage until the human re-applies or restores.
  - Postgres on the same host as the app: one host fault takes both, and the daily snapshot is the only backup (RDS is the Phase 3 upgrade).
  - A public URL on a shared wildcard-DNS name: certificate rate limits and the name's availability belong to a third party.
  - Reviewers in Australia reach a US-east server: this adds latency but not a correctness risk against the 5 second target (spec §5); the smoke check (D21) measures it.
  - The limits of decision 8 (the owner can disable the triggers) and decision 9 (counters reset on restart).
  - The first real check of every AWS detail is the human's first apply.

  **E. Postgres version pin**
  - Postgres **16** is the one major version used in the dev container, the CI service and the Compose stack (human-confirmed with issue #139; 16 is the version the kit's Compose recipe uses).
  - The exact image tag is **checked at the dev-container sitting (D0), not assumed** here (`VERIFY:`). The dev-container password is a throwaway that is never reused in the deployment. CI stays the evidence of record, and the default test run must still pass without Postgres.

  **F. What must never be held, and what enforces each rule (spec §5)**

  | Place | Must never hold | Enforced by |
  |---|---|---|
  | The image and the repository | The ingest key, the seeded passwords, the token signing secret, the database password; a long-lived cloud key | Deployed-mode start-up refusal and the weak-secret check: issue #141 (D3). The image file listing check: Deploy item D10 (not filed yet) |
  | Terraform state and its outputs | A database password, the ingest key, a seeded password, the token signing secret (no secret value in an output; secrets are created by the human outside Terraform) | Review of outputs in each Terraform issue; no secret variable is declared. The start-up refusal in #141 (D3) is the runtime backstop |
  | GitHub secrets | A long-lived cloud key; any application secret | The OIDC-only credential check: Deploy item D16 (not filed yet) |

  Until D10 and D16 are filed and merged, the rows naming them have no automatic check. This record says so rather than claiming one, and the Deploy issues for the Terraform lane and the image must not be approved without their check named in the criteria.

- **Reason:**
  1. (Decision 8) Spec §5 says the audit trail is append-only on any supported database, and the database is the layer that holds even if application code is wrong; the SQLite rule is the same shape (three triggers, plus truncate on Postgres).
  2. (Decision 9) One server and one container make shared counters unnecessary, and in-process counters are the smallest change.
  3. (Decision 10) An apply role that can write IAM could widen its own reach, which spec §5 forbids.
  4. (Region) The human's ruling of 2026-11-13.
  5. (Pin) One major version keeps tests and the deployment on the same engine, and 16 is still supported.
  6. (Never-hold table) A rule left to review alone is not kept; each one names a later check.
- **Alternatives:**
  1. (Decision 8) Privileges only, no triggers: protects against the application role but not against the owner, and gives no truncate or overwrite refusal on its own; both together are the Phase 3 hardening. Guard in application code only: one layer, refuses nothing sent as raw SQL.
  2. (Decision 9) Counters in the database: survive restarts, but more code and more writes per request.
  3. (Decision 10) Keep the instance role in the CI-applied part: simpler, but breaks spec §5.
  4. (Region) `ap-southeast-2`, the home region: closer to reviewers, not chosen by the human.
  5. (Pin) A newer major version: not needed; the recipe and plan assume 16.
- **Trade-offs:**
  1. (Decision 8) A superuser or the table owner can still disable the triggers (stated above). Two database roles must be created in Compose and in production. Postgres trigger syntax differs from SQLite, so the two rules are kept in step by tests on both.
  2. (Decision 9) Limits reset on restart, and a second worker or replica would multiply them; the start command pins one worker.
  3. (Decision 10) Any later change to the instance's permissions is a manual apply by the human.
  4. (Region) Latency for reviewers in Australia (see the accepted risks).
  5. (Pin) The tag must be checked at the dev-container sitting; until then it is unverified.
  6. The record states rules whose checks (D10, D16) do not exist yet; the rules are binding now, the checks follow.
