# Decision: Web framework and database for SOCBoard

One file per choice that may be revisited. Proposed during planning; **needs the human's approval before any build issue uses it** (AGENTS.md: "The web framework and database are not chosen yet; don't add either without an approved spec or issue").

- **Decision:** Backend on **FastAPI** (Python 3.12, already the project's language) serving a JSON API and the built frontend; persistence on **SQLite via SQLAlchemy** for Core, kept database-agnostic so Postgres can replace it for deployment. Frontend a **React + TypeScript single-page app**, with the base generated by **Lovable** (its default stack is React + Vite + TypeScript + Tailwind + shadcn/ui, which matches this choice) from the spec, then kept to frontend + a mock service layer. Real-time delivery is **polling** (not WebSockets) for Core.
- **Reason:** FastAPI gives a typed API, auto OpenAPI docs, and easy OpenTelemetry auto-instrumentation — the exact path the development and devops processes assume. SQLAlchemy + SQLite is the lightest local store and, per the deployment process, swaps to Postgres via one env var without a rewrite. The rule-based, no-ML design means no heavy data/ML stack is needed. Lovable is chosen for the frontend base because it produces owned, exportable React/TS code in our exact stack and makes sensible dashboard-style UI choices, matching the development-example process; the detailed spec gives it a strong initial prompt. Guidance for prompting it is a deliverable: `_docs/planning/lovable-guidance.md`.
- **Alternatives:**
  - *Backend:* Flask or Django. Flask is lighter but lacks FastAPI's typing/OpenAPI/async story; Django is heavier than this app needs. A non-Python stack is allowed by the task but would fight the existing `uv`/pytest/agent-kit setup.
  - *Database:* start directly on Postgres (more prod-like but heavier locally); or a document store (no benefit for this relational, audit-trail-heavy data).
  - *Frontend:* server-rendered templates (Jinja + htmx) instead of a SPA — simpler and one deployable, but a weaker "frontend" story for the rubric and harder to make the queue feel live; recorded as the fallback if the SPA proves too heavy.
  - *Frontend generator:* hand-writing React, or another generator (v0, Bolt, Replit). Lovable is preferred for its design quality and exact-stack output; a coding agent could scaffold instead but tends to make arbitrary choices.
  - *Real-time:* WebSockets/SSE for push instead of polling (deferred — polling is enough for Core and far easier to test and instrument).
- **Trade-offs:** FastAPI + SPA is slightly more setup than templates, but it matches every downstream process doc and the rubric's full-stack expectation. Polling trades true-push immediacy for testability and simpler observability; acceptable for Core and revisitable as a Target Enhancement. Lovable accelerates the frontend base but has two implications to manage: (1) it defaults to a Supabase backend/auth, which we do **not** use — keep it to frontend + mock service; (2) its GitHub integration does two-way sync on the **default branch** of the repo it connects to — so let Lovable own its **own** repo, then clone it and copy the frontend into `frontend/` here (without Lovable's `.git`), committing it as a normal reviewed commit. Both are covered in `_docs/planning/lovable-guidance.md`.
- **Evidence:** `_docs/specs.md` (requirements, invariants, scope); `_docs/planning/02_development.md` and `03_deployment.md` (processes these choices follow). No build issue should adopt this until the human approves.
