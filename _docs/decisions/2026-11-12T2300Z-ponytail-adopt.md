# Decision: Use ponytail in normal work, judged by the human; shelve the trial

One file per choice that may be revisited. **Status: approved** by the human on 2026-11-12 in the orchestrator session. Supersedes `_docs/decisions/2026-11-06T0024Z-ponytail-trial.md`.

- **Decision:** Shelve the pre-registered ponytail trial and use both of its functions in everyday Core work. The trial was considered and its plumbing built, but it was not fully implemented. Its documents stay in place so it can be resumed later (steps in `_docs/planning/roadmap-2-ponytail-trial.md`).
  - The Engineer loads the core skill by path (`_docs/vendor/ponytail/ponytail.md`) before implementing, at level `full`.
  - After the last QA PASS, the orchestrator launches the read-only Reviewer (`_docs/team/reviewer.md`, which applies `_docs/vendor/ponytail/ponytail-review.md`) and posts its report on the issue.
  - The human decides which findings, if any, to apply, and judges over the development cycle whether ponytail helps.
  - No epochs, control issues, metrics script runs or measurement records.
- **Reason:** The trial's rules, which allow no change to a role's rules or commands while a counted issue runs, made the work serial and slow. In the week it ran, it produced plumbing and baseline issues only: no shadow review was ever run (none of #8, #51, #9, #10, #11 or #12 has a reviewer comment), and no issue was marked `ponytail: on`. Using both functions on every issue gives the human direct evidence at the cost of one Reviewer launch per issue.
- **Precedence:** `AGENTS.md`, the role files and the issue's acceptance criteria win over the skill. In particular, the role file's "write tests for what you built, including the cases a limit must refuse" stands over the skill's "one small test". The skill's `ultra` level (questioning the request) is not used, because grooming and the human's approval settle scope. Its `shortcut:` comment form is allowed.
- **Placement:** both skill files sit in `_docs/vendor/ponytail/`, where no tool discovers them, and are read by path. The core skill's description invites loading on any coding task, reviews included. Put in `.claude/skills/`, `.opencode/skills/` or `.kiro/skills/`, it would load into QA's and the PM's sessions too, and those folders (except `.kiro/`) are protected.
- **Alternatives:** finish the trial (Phase 1 needs five shadow reviews, then a treatment phase: weeks, with the epoch rules kept); stop and drop ponytail (gains nothing, and nothing was ever tried); use only the Reviewer (half the test); install the vendor's plugin (always-on injection into every role, third-party code in the agent loop; rejected in the trial decision and still rejected).
- **Trade-offs:** No measurement, so the human's judgment is the only evidence; it is not comparable with the vendor's figures, and none is claimed. One extra launch per issue. The Reviewer's findings are advice: applying one is Engineer work, and QA re-checks what changed (`process.md`, Lifecycle step 7).
- **Write-up (the trial protocol's commitment to publish regardless):** the trial was shelved before Phase 1 had any reviewer data. Result: none yet; inconclusive, not negative. If it is resumed, run the shadow review from the first counted issue, and land process changes before the epoch starts rather than during it. The human's informal use primes the Engineer, so a resumed trial starts a new epoch.
- **Measurement for review (to quantify the benefit):** a light before-and-after comparison replaces the trial. It adds no epochs and no rule on what may change.
  - **Baseline, no ponytail:** #8, #51, #9, #10, #11 and #12, the trial's control issues.
  - **Comparison:** the Core issues claimed after the `AGENTS.md` line that switches ponytail on is committed. #13 is left out of both groups, because it was claimed before the switch.
  - **Figures, per issue, from `make ponytail-metrics N=<n>` (git and GitHub only; run `git fetch origin` first, because it needs the QA PASS commit locally):** non-test lines changed per acceptance criterion, which is the protocol's primary metric; tests added per criterion; QA FAIL rounds; and defects found after PASS. Raw values come first.
  - **Reviewer findings:** at the decision point the human labels each one `useful`, `correct-minor`, `wrong` or `harmful if followed`, and notes whether QA had already raised it. The label is recorded in the session summary as `Finding <issue>-<n>: <label>`.
  - **Review:** at a sweep after about five issues with ponytail, a PM puts the two groups side by side in a measurement record (`_docs/records/<timestamp>-measure-ponytail-review.md`), and the human decides.
  - **Limits, stated in the record:** different issues, tools and models, and process edits between the two groups. The comparison is directional only, never "proven". If it shows a promising difference, the shelved trial is the way to confirm it.
- **Shelved trial documents:** these stay in place and unchanged, apart from status notes: `_docs/planning/ponytail-trial-protocol.md`, `_docs/planning/roadmap-2-ponytail-trial.md`, `_docs/decisions/2026-11-06T0024Z-ponytail-trial.md`, `_docs/records/2026-11-10T1506Z-measure-ponytail-epoch-1-start.md`, `scripts/ponytail_metrics.py` (`make ponytail-metrics`) and `_docs/planning/epoch-batch-1/`.
